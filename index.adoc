= Ada on the Raspberry Pi Pico

image::pico.jpg[Raspberry Pi Pico,width=400,role="related right",title="Raspberry Pi Pico",caption="",link="/img/pico.jpg"]

This project provides libraries and examples for the https://en.wikipedia.org/wiki/Ada_(programming_language)[Ada programming language] on the https://www.raspberrypi.com/documentation/microcontrollers/microcontroller-chips.html[RP2040 and RP2350] microcontrollers and the https://www.raspberrypi.com/documentation/microcontrollers/pico-series.html[Raspberry Pi Pico and Pico 2] development boards.

Code snippets included here are meant to be illustrative but cannot be compiled standalone. For working examples, see https://github.com/JeremyGrosser/pico_examples[pico_examples].

This document assumes you are familiar with the Ada language. If you are new to Ada, https://learn.adacore.com/courses/intro-to-ada/index.html[learn.adacore.com] has an excellent introduction.

If you are upgrading an existing project, see xref:migrating_from_2_x[Migrating from 2.x].

== Getting Started

=== Install Alire
The https://alire.ada.dev/[Alire] package manager is used to manage dependencies and build software using these libraries. You will need to https://alire.ada.dev/docs/#installation[download and install Alire] before continuing.

Assuming you are running Linux on x86_64, the following commands should work.

[source,shell]
----
curl -L -O https://github.com/alire-project/alire/releases/download/v2.1.0/alr-2.1.0-bin-x86_64-linux.zip
unzip alr-2.1.0-bin-x86_64-linux.zip
sudo cp bin/alr /usr/local/bin
----

[#create_a_new_project]
=== Create a new project
Use Alire to create a skeleton project, then add dependencies on an Ada runtime for your chip and on rp2040_hal.

[source,shell]
----
alr init --bin hello_pico
cd hello_pico
alr with light_tasking_rp2040
alr with rp2040_hal --use=https://github.com/JeremyGrosser/rp2040_hal --branch=3.x
----

If Alire prompts you to install tools like unzip and git, accept these changes. If prompted to select a toolchain, choose the most recent versions of `gnat_arm_elf` and `gprbuild`.

The runtime crate provides the startup code, linker script, and clock configuration for your board. It defaults to the Raspberry Pi Pico. See xref:ada_runtime[Ada runtime] for the other runtimes you can choose from and xref:custom_board_support[Custom board support] for other boards.

Next, edit `hello_pico.gpr` to import the runtime project and add the Target, Runtime, and Linker configuration near the top.

[source,ada]
----
with "config/hello_pico_config.gpr";
with "runtime_build.gpr";
project Hello_Pico is
    for Target use Runtime_Build'Target;
    for Runtime ("Ada") use Runtime_Build'Runtime ("Ada");
    package Linker is
        for Switches ("Ada") use Runtime_Build.Linker_Switches & ("-Wl,--gc-sections");
    end Linker;

    for Source_Dirs use ("src/", "config/");
----

Build the project.

[source,shell]
----
alr build --development
----

Alire https://alire.ada.dev/docs/#build-profiles-and-switches[build profiles] affect various compile flags and runtime options. Add `--development`, `--validation`, or `--release` to the `alr build` command to select a default build profile.

If the build was successful, there will be an ELF binary in `./bin/hello_pico`.

==== Pico 2 and other RP2350 boards
For an RP2350, depend on an RP2350 runtime instead.

[source,shell]
----
alr with light_tasking_rp2350
----

Then tell rp2040_hal which chip you're using by adding the `Device` configuration variable to your project's `alire.toml`. The Pico 2 uses the RP2350A. See xref:supported_devices[Supported devices] for the other values.

[source,toml]
----
[configuration.values]
rp2040_hal.Device = "RP2350A"
----

Everything else in this section is the same for both chips.

=== Flashing the Pico
https://www.youtube.com/watch?v=g3sGKoLafew[Raspberry Pi SWD Debug Setup (YouTube)]

There are several ways to get your compiled code onto the Pico. It is highly recommended that you setup a Serial Wire Debug (SWD) debugger so that you can run GDB. The linked video shows how to setup a Raspberry Pi Zero as a SWD debugger, but other debug adapters like the https://www.raspberrypi.com/documentation/microcontrollers/debug-probe.html[Raspberry Pi Debug Probe] or the https://www.segger.com/products/debug-probes/j-link/[Segger J-Link] should work.

Using GDB, you can load the ELF binary and run it. If you are not using an OpenOCD based debugger, these commands may be slightly different. Consult your debugger's documentation if this doesn't work.

----
eval $(alr printenv)
arm-eabi-gdb bin/hello_pico
target extended-remote localhost:3333
monitor arm semihosting enable
load
run
----

https://github.com/raspberrypi/picotool[picotool] can convert a compiled ELF binary to UF2 format, which can be loaded onto the Pico over USB after holding the BOOTSEL button. If you choose this option, you will not be able to debug your code when it crashes.

----
picotool uf2 convert bin/hello_pico -t elf bin/hello_pico.uf2
sudo picotool load bin/hello_pico.uf2
----

The runtime implements `Ada.Text_IO` with semihosting, which sends output to the debugger. Calling `Put_Line` without a debugger attached triggers a HardFault, so remove any `Ada.Text_IO` calls before loading a program over USB.

=== Blinking an LED
You've probably noticed that we haven't written any code yet! Let's change that with the traditional blinking LED demo.

Edit `src/hello_pico.adb`

[source,ada]
----
with RP.GPIO;

procedure Hello_Pico is
   LED : RP.GPIO.GPIO_Point := (Pin => 25);
begin
   LED.Configure (RP.GPIO.Output);

   loop
      LED.Toggle;
      delay 0.25;
   end loop;
end Hello_Pico;
----

The Ada runtime configures the crystal oscillator, PLLs, and system clock before your program starts, so there is no clock or timer initialization to do. On the Pico, the CPU runs at 125 MHz. On the Pico 2, it runs at 150 MHz.

By default, all of the GPIO pins are inputs, so we configure GPIO 25, which is connected to the LED on both the Pico and Pico 2, as an output.

The loop toggles the LED on and off every 250 milliseconds. The `delay` statement is implemented by the runtime using a hardware timer interrupt, so the CPU is free to run other tasks, or sleep, until the delay expires. Use `alr build` to recompile the project and load it using your debugger. If all goes well, the onboard LED will blink!

== Development Guide

=== Source repositories
- https://github.com/JeremyGrosser/rp2040_hal[rp2040_hal] contains drivers for the onboard peripherals of the RP2040 and RP2350.
- https://github.com/JeremyGrosser/pico_bsp[pico_bsp] provides pin definitions and drivers for the Raspberry Pi Pico development board and compatible addons.
- https://github.com/JeremyGrosser/pico_examples[pico_examples] demonstrates the functionality of rp2040_hal and pico_bsp and serves as a template for new projects.
- https://github.com/damaki/community-bb-runtimes[community-bb-runtimes] provides the Ada runtimes, startup code, and linker scripts. It is maintained separately from this project.

=== Versioning
Releases are tagged and added to the Alire index regularly. We follow the https://devhints.io/semver[Semver] pattern, so the API provided by these drivers can be considered stable unless the major version number changes.

This documentation relates to the `3.x` branch of the source repositories and may differ from what's available in Alire. If you need to use unreleased features or fixes, you can pin your project to the `3.x` branch.

----
alr pin --use=https://github.com/JeremyGrosser/rp2040_hal --branch=3.x rp2040_hal
----

The 2.x releases are maintained on the `2.x` branch, which will continue to accept bug fixes. Projects that depend on `rp2040_hal = "^2"` are not affected by the 3.0 release and do not need to change.

The 2.x branch does not include any AI generated code. 3.x may include AI generated code, at the discretion of the maintainer.

[#ada_runtime]
=== Ada runtime
A runtime is the library that implements the parts of the Ada language that need support code, such as tasking, delays, exceptions, and interrupt handlers. rp2040_hal depends on the runtimes from https://github.com/damaki/community-bb-runtimes[community-bb-runtimes], which provide:

- Startup code, the second stage bootloader, and the linker script
- Crystal oscillator, PLL, and clock configuration
- Timekeeping, through `delay` statements and `Ada.Real_Time`
- Interrupt handlers, through protected procedures
- Starting the second CPU core and scheduling tasks on it

The runtimes are published as Alire crates. There is one for each combination of chip and runtime profile.

[cols="1,1,1,3",title="Runtime crates"]
|===
|Profile
|RP2040
|RP2350
|Features

|light-tasking
|`light_tasking_rp2040`
|`light_tasking_rp2350`
|Tasks, protected objects, `Ada.Real_Time`, and interrupt handlers, restricted to the Jorvik profile. No exception propagation. The heap can allocate but not free.

|embedded
|`embedded_rp2040`
|`embedded_rp2350`
|Everything in light-tasking, plus exception propagation and a heap with `Unchecked_Deallocation`.
|===

The serial drivers use `Ada.Real_Time` to implement timeouts, so rp2040_hal needs one of the tasking runtimes. The `light_rp2040` and `light_rp2350` runtimes do not include `Ada.Real_Time` and cannot be used.

To use a runtime, add it as a dependency and reference `runtime_build.gpr` from your project file as shown in xref:create_a_new_project[Create a new project]. The https://github.com/damaki/community-bb-runtimes/blob/main/rp2040_src/README.md[RP2040] and https://github.com/damaki/community-bb-runtimes/blob/main/rp2350_src/README.md[RP2350] runtime documentation describes every configuration option.

==== Reserved resources
The runtime uses a few peripherals for itself. Your application must not reconfigure them.

- One alarm of the system timer implements `Ada.Real_Time` and `delay`. By default this is `ALARM3`, of `TIMER0` on the RP2350.
- With both cores in use, the RP2040 runtime reserves the SIO FIFO and `SPINLOCK31`. The RP2350 runtime reserves the SIO doorbell.
- The clock tree is configured at startup. See xref:clock_configuration[Clock configuration].

[#stack_size]
==== Stack size
The main procedure runs in the environment task, which has a 2 KB stack by default. Large objects, like sample buffers or a strip of LED data, should be declared in a package rather than as local variables of the main procedure, or they will overflow the stack. The size of the environment task's stack can be changed by defining the `__stack_size` linker symbol.

[source,ada]
----
package Linker is
   for Switches ("Ada") use Runtime_Build.Linker_Switches &
      ("-Wl,--gc-sections",
       "-Wl,--defsym=__stack_size=16384");
end Linker;
----

Tasks have their own stacks, sized with the `Storage_Size` aspect.

==== Tasking profile
The http://www.ada-auth.org/standards/rm12_w_tc1/html/RM-D-13.html[Ravenscar] and Jorvik profiles restrict tasking to a subset that can be implemented by a small, predictable runtime. Tasks and protected objects must be declared at library level, tasks never terminate, and there is no rendezvous. Jorvik is a slightly relaxed version of Ravenscar that was added in Ada 2022, and is the profile these runtimes implement.

[quote, John Barnes, Rationale for Ada 2005 section 5.4]
____
The purpose of the Ravenscar profile is to restrict the use of many tasking facilities so that the effect of the program is predictable. The profile was defined by the International Real-Time Ada Workshops which met twice at the remote village of Ravenscar on the coast of Yorkshire in North-East England. A general description of the principles and use of the profile in high integrity systems will be found in an ISO/IEC Technical Report and so we shall not cover that material here.

It is reputed that the hotel in which the workshops were held was originally built as a retreat for King George III to keep a mistress. Another odd rumour is that he ordered all the natural trees to be removed and replaced by metallic ones whose metal leaves clattered in the wind. It also seems that Henry Bolingbroke landed at Ravenscar in July 1399 on his way to take the throne as Henry IV. Ravenscar is mentioned several times by Shakespeare in Act II of King Richard II; it is spelt Ravenspurg which is slightly confusing – maybe we need the ability to rename profile identifiers.
____

The https://learn.adacore.com/courses/Ada_For_The_Embedded_C_Developer/chapters/03_Concurrency.html[Concurrency and Real-Time] document provides several examples of tasks and protected objects. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/ravenscar_blink[ravenscar_blink] example blinks an LED from a task.

[#interrupts]
=== Interrupts
Interrupt handlers are protected procedures with the `Attach_Handler` aspect. The runtime installs the handler and enables the interrupt in the NVIC while the program elaborates, so there is nothing to register at run time. The protected object must be declared at library level, in a package.

Interrupt names are defined by the runtime in `Ada.Interrupts.Names`. Every interrupt has two names, ending in `_CPU_1` and `_CPU_2`, which select the core that runs the handler.

[source,ada]
----
with Ada.Interrupts.Names;
with System;

package Handlers is
   protected UART_0
      with Interrupt_Priority => System.Interrupt_Priority'Last
   is
      procedure Handler
         with Attach_Handler => Ada.Interrupts.Names.UART0_Interrupt_CPU_1;
   end UART_0;
end Handlers;
----

The drivers provide procedures to enable, test, and acknowledge the interrupt sources of each peripheral, such as `RP.GPIO.Interrupt.Enable`, `RP.UART.Enable_IRQ`, and `RP.PWM.Enable_Interrupt`. A handler is called for every source that shares the interrupt, so it should check which one fired and acknowledge it. See xref:gpio_interrupts[GPIO interrupts] for a complete example.

Protected entries let a task block until an interrupt occurs, rather than polling. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/uart_interrupt[uart_interrupt] example uses this to wait for received characters.

=== Hardware overview
The Raspberry Pi RP2040 is a dual core https://en.wikipedia.org/wiki/ARM_Cortex-M#Cortex-M0+[ARM Cortex-M0+] microcontroller. Detailed specifications and low level documentation can be found in the https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf[RP2040 datasheet].

The RP2350 is its successor, with two https://en.wikipedia.org/wiki/ARM_Cortex-M#Cortex-M33[ARM Cortex-M33] cores, more memory, a third PIO block, and more PWM slices. The larger package has 48 GPIO pins. The https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf[RP2350 datasheet] is the reference for this chip. Section numbers in this document refer to the RP2040 datasheet unless noted otherwise.

[#pico_pinout]
==== Pico pinout
image::Pico-R3-SDK11-Pinout.svg[Pin diagram,link="/img/Pico-R3-SDK11-Pinout.svg",title="Pin diagram"]

The Raspberry Pi Pico is a low cost development board that includes the RP2040, a micro USB port, crystal oscillator, voltage regulator, and a green LED. The https://datasheets.raspberrypi.com/pico/pico-datasheet.pdf[Pico datasheet] includes schematics, pinout diagrams, and design recommendations.

The Pico 2 has the same form factor and pinout with an RP2350A in place of the RP2040. See the https://datasheets.raspberrypi.com/pico/pico-2-datasheet.pdf[Pico 2 datasheet].

If you wish to develop a custom board using the RP2040, the https://datasheets.raspberrypi.com/rp2040/hardware-design-with-rp2040.pdf[hardware design guide] contains reference designs and layout tips.

=== Clock configuration

image::clock_tree.png[Clock tree,link="/img/clock_tree.png",title="Clock tree"]

See section 2.15 of the https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf[RP2040 datasheet] for a detailed description of the clock hierarchy.

The runtime starts the crystal oscillator and PLLs before your program is elaborated. The clocks that feed individual peripherals are gated off until a driver needs them. Each driver enables its own clock when it is configured, so most programs never need to call https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-clock.ads[RP.Clock] directly.

The system clock frequency is set by the runtime's PLL configuration variables in `alire.toml`. This example changes the RP2040's system clock to 133 MHz. Replace `light_tasking_rp2040` with the name of the runtime crate you're using.

[source,toml]
----
[configuration.values]
light_tasking_rp2040.PLL_Sys_Reference_Div = 1
light_tasking_rp2040.PLL_Sys_VCO_Multiple = 133
light_tasking_rp2040.PLL_Sys_Post_Div_1 = 6
light_tasking_rp2040.PLL_Sys_Post_Div_2 = 2
----

The `RP.Clock.Frequency` function uses the internal frequency counter to measure internal clocks. This is used to configure dividers and enforce minimum operating frequencies in preconditions. Most drivers provide convenience wrappers that perform these calculations for you.
[source,ada]
----
declare
    Target_Frequency : constant Hertz := 1_000_000;
    Divider          : constant Positive := Positive (RP.Clock.Frequency (RP.Clock.SYS) / Target_Frequency);
begin
    Put_Line (Divider'Image);
end;
----

==== Clock output
Internal clocks can be divided and driven onto a pin with one of the four GPOUT clock generators. The pin needs to be configured with the `CLK` function. This example outputs a 10 MHz clock on GPIO 21 of a Pico. See the https://github.com/JeremyGrosser/pico_examples/tree/3.x/clock_output[clock_output] example.
[source,ada]
----
declare
    use RP.Clock;
    use RP.GPIO;
    GP21 : constant GPIO_Point := (Pin => 21);
begin
    GP21.Configure (Output, Pull_Up, CLK, Slew_Fast => True);
    Set_Source (GPOUT0, SYS);
    Set_Divider (GPOUT0, 12.5);
    Enable (GPOUT0);
end;
----

The set of clock sources and the resolution of the divider differ between the RP2040 and RP2350, so `RP.Clock` has a separate specification for each chip.

=== GPIO
image::pad-config.png[IO pad diagram,title="IO pad diagram",link="/img/pad-config.png"]
The RP2040 and RP2350A have 30 GPIO pins. The RP2350B has 48. The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-gpio.ads[RP.GPIO] package implements the abstract https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-gpio.ads[HAL.GPIO] interface.

[source,ada]
----
type GPIO_Pin is range 0 .. RP.Device_Parameters.Pin_Count - 1;
type GPIO_Point is new HAL.GPIO.GPIO_Point with record
    Pin : GPIO_Pin;
end record;
----

==== Naming pins
BSP packages contain names for pins that map to a schematic net name or silkscreened label familiar to the user. For example, `package Pico` from pico_bsp contains the following definitions that match the board's documentation.
[source,ada]
----
   GP25 : aliased GPIO_Point := (Pin => 25);
   GP26 : aliased GPIO_Point := (Pin => 26);
   GP27 : aliased GPIO_Point := (Pin => 27);
   GP28 : aliased GPIO_Point := (Pin => 28);

   LED  : GPIO_Point renames GP25;
----

The examples in this document use these names. If your project doesn't depend on pico_bsp, declare a `GPIO_Point` for each pin you use.

==== Basic operation
`RP.GPIO.Configure` has several optional parameters. The default values will configure the pin for basic `Get`, `Set`, `Clear`, `Toggle` operation. The IO peripherals are taken out of reset the first time a pin is configured.
[source,ada]
----
Pico.LED.Configure (RP.GPIO.Output);
loop
    Pico.LED.Toggle;
end loop;
----

==== Pin functions
The `Func` parameter connects the pin to an internal peripheral, such as I2C. See *2.19.2. Function Select* in the RP2040 datasheet or the xref:pico_pinout[Pico pin diagram] for the mapping between pins and peripherals. This example also shows how Ada's `renames` can be used to make it clear what a pin will be used for.
[source,ada]
----
declare
    use RP.GPIO;
    SCL : GPIO_Point renames Pico.GP27;
    SDA : GPIO_Point renames Pico.GP26;
begin
    SCL.Configure
        (Mode       => Output,
         Pull       => Pull_Up,
         Func       => I2C,
         Schmitt    => True,
         Slew_Fast  => False);
    SDA.Configure
        (Mode       => Output,
         Pull       => Pull_Up,
         Func       => I2C,
         Schmitt    => True,
         Slew_Fast  => False);
end;
----

The `HSTX`, `PIO2`, and `UARTN` functions only exist on the RP2350. The PIO function for a given PIO block is returned by `RP.PIO.GPIO_Function`.

==== Low level interface
`RP.GPIO` also exposes each pad and IO control individually, as procedures that take a `GPIO_Pin`. These are useful when you need to change one property of a pin without disturbing the rest, or need a combination that `Configure` doesn't offer.

[source,ada]
----
declare
    use RP.GPIO;
    Pin  : constant GPIO_Pin := 15;
    High : Boolean;
begin
    Isolate (Pin, False);      --  Release the pad isolation latch (RP2350 only)
    Func (Pin, SIO);
    Pull (Pin, Up => True);
    Drive (Pin, Drive_8mA);
    Output_Enable (Pin, False);
    Input_Enable (Pin, True);
    Get (Pin, High);
end;
----

On the RP2350, pads are isolated from the IO logic after reset. `Configure` removes the isolation for you. `Isolate` has no effect on the RP2040.

[#gpio_interrupts]
==== GPIO interrupts
Level and edge triggered interrupts are controlled by the nested `RP.GPIO.Interrupt` package. All of the pins share a single interrupt for each core, `IO_IRQ_BANK0`, so the handler checks which pin and trigger caused it. Edge triggered interrupts remain pending until they are acknowledged. Level triggered interrupts remain pending for as long as the pin stays at that level.
[source,ada]
----
with Ada.Interrupts.Names;
with System;
with RP.GPIO;
with Pico;

package Handlers is
    Button : RP.GPIO.GPIO_Point renames Pico.GP9;

    protected GPIO
        with Interrupt_Priority => System.Interrupt_Priority'Last
    is
        procedure Handler
            with Attach_Handler => Ada.Interrupts.Names.IO_IRQ_BANK0_Interrupt_CPU_1;
    end GPIO;
end Handlers;

package body Handlers is
    protected body GPIO is
        procedure Handler is
            use RP.GPIO.Interrupt;
        begin
            if Triggered (Button.Pin, Falling) then
                Acknowledge (Button.Pin, Falling);
                Pico.LED.Toggle;
            end if;
        end Handler;
    end GPIO;
end Handlers;
----

The interrupt is enabled for a pin and trigger from the main program.
[source,ada]
----
Handlers.Button.Configure (RP.GPIO.Input, RP.GPIO.Pull_Up);
RP.GPIO.Interrupt.Enable (Handlers.Button.Pin, RP.GPIO.Interrupt.Falling);
----

`Enable` and `Disable` take an optional `CPU` parameter that selects which core's interrupt the pin is routed to. It must match the name used in `Attach_Handler`. `Enable_Wake` allows a pin to wake the chip from dormant mode. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/gpio_interrupts[gpio_interrupts] example contains a complete project.

=== Timing

==== Delays and Ada.Real_Time
Delays and timekeeping are provided by the Ada runtime rather than by a driver. `delay` suspends the calling task for a number of seconds.
[source,ada]
----
delay 0.5;
----

`Ada.Real_Time` provides a monotonic clock, counting from power on. A common pattern is to use `delay until` to ensure that a loop executes on a fixed schedule, no matter how long the work in the loop takes.
[source,ada]
----
declare
    use Ada.Real_Time;
    T : Time := Clock;
begin
    loop
        T := T + Milliseconds (100);
        delay until T;

        --  Do some work here. As long as it takes less than 100ms to execute,
        --  this loop will run at precise 100ms intervals.
    end loop;
end;
----

Both forms of delay are implemented with a timer interrupt, so other tasks run while one is waiting, and the CPU sleeps if there's nothing to do. `delay` statements are not allowed inside protected operations, including interrupt handlers.

==== Timer
The Timer peripheral runs at 1 MHz (1 microsecond per tick) and counts up from zero at power on. The counter is 64 bits wide and https://www.wolframalpha.com/input/?i=2**64+microseconds+in+years[will not overflow in your lifetime]. On the RP2040, the https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-timer.ads[RP.Timer] package reads this counter directly.

`Clock` returns the current value of the timer, microseconds since power on.
[source,ada]
----
declare
    Now : constant RP.Timer.Time := RP.Timer.Clock;
begin
    Put_Line (Now'Image);
end;
----

`Busy_Wait_Until` polls `Clock` until a deadline is reached. It doesn't use interrupts, so it works in places where a `delay` statement is not allowed, at the cost of keeping the CPU busy.
[source,ada]
----
declare
    use type RP.Timer.Time;
begin
    RP.Timer.Busy_Wait_Until (RP.Timer.Clock + 50); --  50 microseconds
end;
----

For delays that don't keep the CPU busy, use `delay` and `Ada.Real_Time`. `RP.Timer` is not available on the RP2350. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/timer[timer] example shows each of these delays.

==== Real Time Clock (RTC)
The RTC is an RP2040 peripheral. The RP2350 does not have one.

The RTC tracks the date and time in years, months, days, day of week, hours, minutes, and seconds.

The RTC is not running by default, but once initialized, will continue running as long as power is supplied. This means the time can persist through a reset. In most cases, you'll want to check if the RTC is already running before initializing it.
[source,ada]
----
if not RP.Device.RTC.Running then
    RP.Device.RTC.Configure;
end if;
----

https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-rtc.ads[RP.RTC] implements the https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-real_time_clock.ads[HAL.Real_Time_Clock] interface. Date and time are represented by the `RTC_Date` and `RTC_Time` records.

[source,ada]
----
with HAL.Real_Time_Clock; use HAL.Real_Time_Clock;
with RP.Device;

RP.Device.RTC.Set
    (Time =>
        (Hour => 12,
         Min  => 0,
         Sec  => 0),
     Date =>
        (Day_Of_Week => Friday,
         Year        => 21,
         Month       => October,
         Day         => 1));

declare
    Time : RTC_Time;
    Date : RTC_Date;
begin
    RP.Device.RTC.Get (Time, Date);
end;
----

The `RTC_Year` type has the range `0 .. 99`, so you will likely need to add an offset to this value for display purposes. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/rtc[rtc example] includes a https://github.com/JeremyGrosser/pico_examples/blob/3.x/rtc/src/text_format.adb[To_String] function that converts `RTC_Time` and `RTC_Date` into an https://en.wikipedia.org/wiki/ISO_8601[ISO 8601] string.

No support is provided for time zones, leap seconds, or daylight savings time conversion.

`Pause` and `Resume` procedures are provided to temporarily stop the RTC. Note that the `Running` function will return `False` while the RTC is paused. If the chip is reset while the RTC is paused, the `RP.RTC` package cannot differentiate between a paused RTC and an uninitialized one.

`Enable_Alarm` sets a date and time, with a mask selecting which fields are compared, at which the `Alarm` function begins returning `True`.

=== Serial interfaces
The UART, SPI, and I2C drivers implement the https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-uart.ads[HAL.UART], https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-spi.ads[HAL.SPI], and https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-i2c.ads[HAL.I2C] interfaces to provide compatibility with other platforms. The interfaces all have `Transmit` and `Receive` procedures that provide status information to an `out` parameter. The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-uart.ads[RP.UART], https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-spi.ads[RP.SPI], and https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-i2c_master.ads[RP.I2C_Master] packages provide platform specific initialization, configuration, and status procedures that are not included in the HAL interfaces. Timeouts are specified in milliseconds and implemented by polling `Ada.Real_Time.Clock`.

The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-device.ads[RP.Device] package declares a port object for each of the serial peripherals: `UART_0`, `UART_1`, `SPI_0`, `SPI_1`, `I2CM_0`, and `I2CM_1`. All of the serial interfaces require `clk_peri`, which is enabled by each port's `Configure` procedure.

GPIO pins need to be configured for the serial peripherals to interact with the outside world. See the xref:pico_pinout[pin diagram] for information on which pins can be associated with serial functions. All serial pins should use the `Output` mode, regardless of the serial data direction. External pull-up resistors are recommended for buses that require them, rather than exposing the internal pull-ups to bus currents.

==== UART
[source,ada]
----
with HAL.UART;
with RP.UART;
with RP.GPIO; use RP.GPIO;
with RP.Device;
with Pico;

procedure UART_Example is
    UART_TX : GPIO_Point renames Pico.GP0;
    UART_RX : GPIO_Point renames Pico.GP1;
    Port    : RP.UART.UART_Port renames RP.Device.UART_0;

    Message : constant String := "Hello, Pico!";
    Data    : HAL.UART.UART_Data_8b (Message'Range);
    Status  : HAL.UART.UART_Status;
begin
    UART_TX.Configure (Output, Floating, UART);
    UART_RX.Configure (Output, Floating, UART);

    --  The default config is 115200 8n1, this example just overrides the baud rate
    Port.Configure (Config => (Baud => 9600, others => <>));

    for I in Message'Range loop
        Data (I) := Character'Pos (Message (I));
    end loop;

    --  A Timeout of 0 means this procedure may block forever. The default timeout is one second.
    Port.Transmit (Data, Status, Timeout => 0);
end UART_Example;
----

`Send_Break` holds the transmit line low for a number of microseconds, which some protocols use to mark the start of a frame. `Symbol_Time` and `Frame_Time` return the duration of a bit and of a frame at the current configuration, which is useful for calculating the length of a break.

`Enable_IRQ` enables one of the UART's interrupt sources, such as `Receive` or `Transmit`. See xref:interrupts[Interrupts] for how to attach a handler, and the https://github.com/JeremyGrosser/pico_examples/tree/3.x/uart_interrupt[uart_interrupt] example.

==== SPI
SPI is a synchronous interface. For every word that is transmitted, another is received and buffered simultaneously. The SPI peripheral can buffer up to 8 words in the Transmit and Receive FIFOs. The bus clock is generated when `Transmit` is called. `Receive` should be called after every `Transmit` to read the same number of bytes from the FIFO buffer. If `Receive` is not called after every 8 transmitted words, the receive buffer will overflow and data will be silently dropped.

The chip select signal, often referred to as `CSn`, `CS`, `NSS`, [.overbar]#CS#, or [.overbar]#SS#, is optional. If specified, it will be pulled low while a SPI transfer is in progress. Some SPI devices require this signal to be held low across multiple transfers. For those devices, configure this as a normal output pin and toggle it directly, rather than letting the SPI peripheral control it.

If the `Blocking` configuration flag is `True`, then the `Transmit` and `Receive` procedures will wait until the entire `Data` array has been processed or the timeout has expired before returning. If `Timeout` is set to `0`, these procedures will block forever.

If `Blocking` is `False`, then `Transmit` returns as soon as all words have been delivered to the FIFO, but may not all be clocked out to the bus yet. The SPI peripheral will continue clocking and transmitting words in the background until the transmit FIFO is empty. In non-blocking mode, the `Receive` procedure will copy data from the receive FIFO into the supplied `Data` array until the array is full, the timeout expires, or the receive FIFO is empty. This may result in a partially filled `Data` array. The `Transmit_Status` and `Receive_Status` functions can be used to anticipate the behavior of `Transmit` and `Receive` in non-blocking mode.

[source,ada]
----
with HAL.SPI; use HAL.SPI;
with RP.GPIO; use RP.GPIO;
with RP.SPI;  use RP.SPI;
with RP.Device;
with Pico;

procedure SPI_Example is
    SCK    : GPIO_Point renames Pico.GP2;
    MOSI   : GPIO_Point renames Pico.GP3;
    MISO   : GPIO_Point renames Pico.GP4;
    CS     : GPIO_Point renames Pico.GP5;
    Port   : RP.SPI.SPI_Port renames RP.Device.SPI_0;

    Data   : HAL.SPI.SPI_Data_8b (1 .. 4) := (41, 42, 43, 44);
    Status : HAL.SPI.SPI_Status;
begin
    SCK.Configure (Output, Floating, SPI);
    MOSI.Configure (Output, Floating, SPI);
    MISO.Configure (Output, Floating, SPI);
    CS.Configure (Output, Floating, SPI);
    Port.Configure (Config =>
        (Role      => Master,
         Baud      => 10_000_000, --  up to 50 MHz is supported
         Data_Size => Data_Size_8b,
         Polarity  => Active_Low,
         Phase     => Rising_Edge,
         Blocking  => True,
         Loopback  => False));

    Port.Transmit (Data, Status);
    Port.Receive (Data, Status);
end SPI_Example;
----

The `Transfer` procedure exchanges a single byte, transmitting `Data` and replacing it with the byte that was received. Setting `Loopback` in the configuration connects the transmitter to the receiver internally, which is handy for testing without any wiring.

==== I2C
The I2C peripheral is similar to the other serial interfaces in operation but is more complicated due to the state machine that controls the bus. Pull-up resistors should be added to the SCL and SDA signals. External 4.7k ohm resistors are usually sufficient, but this value may need to be adjusted to keep the rise time within spec. See the https://www.nxp.com/docs/en/user-guide/UM10204.pdf[I2C bus specification] for more information.

The RP2040 datasheet recommends enabling https://en.wikipedia.org/wiki/Schmitt_trigger[Schmitt triggering] for the I2C pins.

The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-i2c_master.ads[RP.I2C_Master] package implements the https://github.com/Fabien-Chouteau/hal/blob/master/src/hal-i2c.ads[HAL.I2C] interface. It supports standard mode (100 kHz), fast mode (400 kHz), and fast mode plus (1 MHz) with 7-bit addresses. Target (slave) operation is not supported.

`HAL.I2C.I2C_Address` is 8 bits wide, with the read/write flag in the least significant bit. A device's 7-bit address needs to be shifted left by one bit. For example, a device with the bus address `2#1110110#` is addressed as `2#1110_1100#`. The driver ignores the read/write bit.

[source,ada]
----
with RP.GPIO; use RP.GPIO;
with RP.I2C_Master;
with RP.Device;
with HAL.I2C;
with Pico;

procedure I2C_Demo is
    Port   : RP.I2C_Master.I2C_Master_Port renames RP.Device.I2CM_0;
    SDA    : RP.GPIO.GPIO_Point renames Pico.GP0;
    SCL    : RP.GPIO.GPIO_Point renames Pico.GP1;
    Data   : HAL.I2C.I2C_Data (1 .. 2) := (others => 0);
    Status : HAL.I2C.I2C_Status;
begin
    SDA.Configure (Output, Floating, RP.GPIO.I2C, Schmitt => True);
    SCL.Configure (Output, Floating, RP.GPIO.I2C, Schmitt => True);
    Port.Configure (Baudrate => 400_000); --  I2C fast mode

    --  The address and data format vary widely depending on the I2C slave
    --  device you're connected to. See your I2C slave's datasheet for details.
    Port.Master_Transmit
        (Addr   => 16#42#,
         Data   => Data,
         Status => Status);
end I2C_Demo;
----

`Mem_Read` and `Mem_Write` transmit a register address, then read or write data without releasing the bus in between. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/i2c_demo[i2c_demo] example uses `Mem_Read` to read the ID register of a sensor.

=== USB device controller
The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-usb_device.ads[RP.USB_Device] package implements the https://github.com/Fabien-Chouteau/usb_embedded/blob/main/src/usb-hal-device.ads[USB.HAL.Device.USB_Device_Controller] interface from the https://github.com/Fabien-Chouteau/usb_embedded[usb_embedded] crate. The controller is declared as `RP.Device.UDC`.

After initialization, all USB events are handled by the `Poll` procedure. Poll should be called regularly in a main loop, or in response to the `USBCTRL` interrupt.

The https://github.com/JeremyGrosser/pico_examples/blob/3.x/usb_echo/src/usb_echo.adb[usb_echo] example configures the USB controller to implement the https://en.wikipedia.org/wiki/USB_communications_device_class[USB serial (CDC ACM)] protocol. https://github.com/JeremyGrosser/pico_examples/tree/3.x/usb_echo_interrupt[usb_echo_interrupt] does the same from an interrupt handler.

=== Pulse Width Modulation (PWM)
image::pwm-pins.png[PWM pin mapping,title="PWM pin mapping",link="/img/pwm-pins.png"]
The RP2040's PWM is split into 8 slices, each slice has 2 channels, and each channel can be output to 2 pins simultaneously. The RP2350 has 12 slices. The B channel of each slice can be configured as an input and used as a gate or trigger for channel A. Even numbered GPIO pins are associated with Channel A and odd numbered pins are Channel B.

The `To_PWM` function can help you find the Slice and Channel associated with a GPIO pin.
[source,ada]
----
with RP.PWM; use RP.PWM;
with RP.GPIO;
with Pico;

procedure PWM_Demo is
    P : constant PWM_Point := To_PWM (Pico.GP0);
begin
    RP.PWM.Initialize;
    Pico.GP0.Configure (RP.GPIO.Output, RP.GPIO.Pull_Up, RP.GPIO.PWM);

    Set_Mode (P.Slice, Free_Running);
    Set_Frequency (P.Slice, 10_000_000);
    Set_Interval (P.Slice, 10_000);
    Set_Duty_Cycle (P.Slice, P.Channel, 5_000);
    Enable (P.Slice);
end PWM_Demo;
----
In this example, the PWM slice is configured to run at 10 MHz with an interval of 10,000. The output frequency is `(Frequency / Interval)`. In this case, 1 KHz. The output will be high as long as the counter is less than or equal to the value passed to `Set_Duty_Cycle`, after which it transitions to low until the counter reaches `Interval`. The counter then resets to zero and begins again. In this example, the duty cycle is half of the interval, so the output has a 50% duty cycle. If the duty cycle is greater than or equal to the interval, the output is high for the entire cycle. If duty cycle is zero, the output is low for the entire cycle. Each channel's output may be inverted using the `Set_Invert` procedure.

All of these parameters may be changed while the clock is running to modulate the output. See section 4.5.2.1. Pulse Width Modulation of the RP2040 datasheet for specifics about when changes to a running PWM slice take effect.

The `Set_Frequency` procedure attempts to calculate the correct divider value to get the desired PWM frequency. This is not always possible as the PWM divider has a fixed resolution. For accurate PWM frequency setting, use the `Set_Divider` procedure in combination with `RP.Clock.Frequency (RP.Clock.SYS)` instead, which uses the `Divider` fixed point type defined with the same resolution and range as the hardware divider. This allows you to calculate the error from the target frequency. Note that this is just the input frequency to the PWM, which will be divided further by the value set by `Set_Interval`.

[source,ada]
----
Input_Clock      : constant Hertz := RP.Clock.Frequency (RP.Clock.SYS);
Target_Frequency : constant Hertz := 1_000_000;
Target_Divider   : constant Float := Float (Input_Clock) / Float (Target_Frequency);
Actual_Divider   : constant RP.PWM.Divider := RP.PWM.Divider (Target_Divider);
Divider_Error    : constant Float := Target_Divider - Float (Actual_Divider);
Actual_Frequency : constant Float := Float (Input_Clock) / Float (Actual_Divider);
Frequency_Error  : constant Float := Float (Target_Frequency) - Actual_Frequency;
----

`Enable_Interrupt` generates an interrupt each time a slice's counter wraps. The handler should call `Acknowledge_Interrupt`. The RP2040 has a single `PWM_IRQ_WRAP` interrupt. The RP2350 has two, `PWM_IRQ_WRAP_0` and `PWM_IRQ_WRAP_1`, selected by the `IRQ` parameter.

=== Analog to Digital Converter (ADC)
The ADC is multiplexed across several channels, one of which is reserved for the internal temperature sensor. The RP2040 and RP2350A have four external channels on GPIO 26 through 29. The RP2350B has eight, on GPIO 40 through 47. The ADC generates 12-bit samples at up to 500,000 samples per second.

`RP.ADC.Enable` turns on the ADC clock and takes the ADC out of reset. It must be called before any other ADC procedure. `Configure` switches the GPIO pin for a channel to analog mode.

==== Configuring the ADC
[source,ada]
----
with RP.ADC;  use RP.ADC;
with Pico;

procedure ADC_Example is
    Channel : constant ADC_Channel := To_ADC_Channel (Pico.GP26);
    Value   : Analog_Value;
begin
    RP.ADC.Enable;
    RP.ADC.Configure (Channel);

    loop
        Value := RP.ADC.Read (Channel);
    end loop;
end ADC_Example;
----

==== Voltage measurement
If a known reference voltage is applied to the `ADC_VREF` pin, the `Read_Microvolts` function can calculate the `Microvolts` integer type for you. On the Pico board, this reference is set to 3.3V unless your board has been modified. This is the default value for the `VREF` parameter.

[source,ada]
----
declare
    use RP.ADC;
    uV : Microvolts;
begin
    uV := RP.ADC.Read_Microvolts
        (Channel => 0,
         VREF    => 3_300_000);
end;
----

==== Temperature sensor
The internal temperature sensor is attached to the last ADC channel, which is named by the `RP.ADC.Temperature_Sensor` constant. The `Temperature` function converts the value of this ADC channel to `Celsius` based on some reference values. See 4.9.5. Temperature Sensor in the https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf[RP2040 datasheet] for accuracy and calibration information.

The `Temperature` function enables the temperature sensor for the duration of the reading and the ADC channel does not need to be configured beforehand.
[source,ada]
----
declare
    C : RP.ADC.Celsius;
begin
    RP.ADC.Enable;
    C := RP.ADC.Temperature;
end;
----

==== Round robin
In round robin mode, the ADC will switch to the next enabled channel after each conversion. This allows you to sample many channels is rapid succession.

[source,ada]
----
RP.ADC.Set_Round_Robin
    (Channels =>
        (0      => True,
         1      => True,
         others => False));
Sample := RP.ADC.Read;  --  Reads channel 0
Sample := RP.ADC.Read;  --  Reads channel 1
Sample := RP.ADC.Read;  --  Reads channel 0
Sample := RP.ADC.Read;  --  Reads channel 1
----

==== Continuous conversion
The ADC can be configured to continuously sample its inputs at a fixed rate. This is useful if you want to capture audio, for example. Sampling begins as soon as `RP.ADC.Set_Mode` is called.

[source,ada]
----
declare
    use RP.ADC;
    Sample : Analog_Value;
begin
    Set_Sample_Rate (48_000);
    Set_Mode (Free_Running);
    --  DMA would be better here, see the adc_continuous example.
    loop
        Sample := RP.ADC.Read;
    end loop;
end;
----

Samples will be dropped if `Read` isn't called fast enough. In most cases, you will want to setup a DMA channel triggered on the ADC to copy samples to a buffer while the CPU does processing. The https://github.com/JeremyGrosser/pico_examples/blob/3.x/adc_continuous/src/adc_continuous.adb[adc_continuous] example demonstrates using DMA and double buffering to capture and process two channels simultaneously.

=== Direct Memory Access (DMA)
The DMA peripheral can copy data from one memory location to another, freeing up the CPU to do other work while a transfer is in progress. A DMA channel is configured with a Source and Target `System.Address` and can be triggered by almost every other peripheral on the chip. The DMA peripheral can increment the source and/or target address after each transfer, or always use the same address. The RP2040 has 12 DMA channels and the RP2350 has 16.

For example, if you had a large buffer that needed to be transmitted via SPI, you could set the Source address to the beginning of the buffer and the target address to the SPI FIFO address, with the DMA channel configured to increment the source address until it reaches the end of the buffer.
[source,ada]
----
with HAL.SPI;
with HAL;
with RP.DMA;  use RP.DMA;
with RP.Device;
with RP.SPI;

package DMA_Demo is
    procedure Run;
end DMA_Demo;

package body DMA_Demo is
    Port    : RP.SPI.SPI_Port renames RP.Device.SPI_0;
    Buffer  : aliased HAL.SPI.SPI_Data_8b (1 .. 512);
    Channel : constant RP.DMA.DMA_Channel_Id := 0;

    procedure Run is
    begin
        --  Fill a buffer with sequential numbers
        for I in Buffer'Range loop
            Buffer (I) := HAL.UInt8 (I mod 255);
        end loop;
        Port.Configure;

        RP.DMA.Enable;
        RP.DMA.Configure
            (Channel => Channel,
             Config  =>
                (Data_Size     => Transfer_8,
                 Read_Address  => Increment,
                 Write_Address => Static,
                 Trigger       => SPI0_TX,
                 others        => <>));
        RP.DMA.Start
            (Channel => Channel,
             From    => Buffer'Address,
             To      => Port.FIFO_Address,
             Count   => Buffer'Length);

        loop
            --  Do some other work while the transfer is in progress

            if not RP.DMA.Busy (Channel) then
                --  Transfer completed, maybe begin another one.
                null;
            end if;
        end loop;
    end Run;
end DMA_Demo;
----

The `DMA_Configuration` record contains many other options such as reading/writing ring buffers, chaining another DMA channel after a transfer has finished, and generating checksums of data transferred through a DMA channel. On the RP2350, addresses can also be decremented after each transfer. See the datasheet for more information on these options.

=== Programmable I/O (PIO)
The PIO peripheral consists of several state machines connected to all of the I/O pins. The RP2040 has two PIO blocks and the RP2350 has three, each with four state machines. The PIO has it's own opcodes and assembly language documented in the RP2040 datasheet. The https://github.com/raspberrypi/pico-sdk/tree/master/tools/pioasm[pioasm] assembler can output assembled code as a .ads file with the compiled binary represented as an array.

----
pioasm -p Hello -o ada src/hello.pio gen/hello.ads
----

The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-pio.ads[RP.PIO] driver is very similar to the interface of the pico-sdk C API, as most available example code and documentation for PIO use that nomenclature. A PIO block is identified by a number of type `RP.PIO.Device`, and a state machine by an `SM_Index`.

[source,ada]
----
declare
    use RP.PIO;
    P      : constant RP.PIO.Device := 0;
    SM     : constant SM_Index := 0;
    Config : SM_Config := Default_SM_Config;
begin
    Pico.LED.Configure (RP.GPIO.Output, RP.GPIO.Floating, GPIO_Function (P));

    Enable (P);
    Load (P, Hello.Hello_Program_Instructions, Offset => 0);

    Set_Out_Pins (Config, Pico.LED.Pin, 1);
    Set_Wrap (Config, Hello.Hello_Wrap_Target, Hello.Hello_Wrap);
    Set_Clock_Frequency (Config, 50_000_000);

    SM_Initialize (P, SM, Initial_PC => 0, Config => Config);
    Set_Pin_Direction (P, SM, Pico.LED.Pin, Output);
    Set_Enabled (P, SM, True);

    Put (P, SM, 1);
end;
----

`Enable` takes the PIO block out of reset and must be called before anything else. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/pio_blink[pio_blink] example demonstrates loading an assembled PIO program and executing it. The https://github.com/JeremyGrosser/pico_examples/tree/3.x/pio_assemble[pio_assemble] example builds the same program at compile time with `RP.PIO.Encoding`, without pioasm.

On the RP2350B, a PIO block can only reach 32 of the 48 pins at a time. `Set_GPIO_Base` selects whether that window starts at GPIO 0 or GPIO 16.

rp2040_hal includes a few drivers built on PIO:

- https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-pio-audio_i2s.ads[RP.PIO.Audio_I2S] generates an I2S audio stream for use with the https://github.com/JeremyGrosser/pico_examples/blob/3.x/pimoroni_audio_pack/src/pimoroni_audio_pack.adb[Pimoroni Audio Pack example]. The PIO program was copied from the https://github.com/raspberrypi/pico-extras[raspberrypi/pico-extras] repository and it's C startup code ported to Ada.
- https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-pio-ws2812.ads[RP.PIO.WS2812] drives strips of WS2812 "NeoPixel" LEDs. See the https://github.com/JeremyGrosser/pico_examples/tree/3.x/ws2812_demo[ws2812_demo] example.
- https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-pio-touch_sense.ads[RP.PIO.Touch_Sense] turns a pin and a resistor into a capacitive touch sensor.

=== Interpolator
image::interp.png[Interpolator data flow,link="/img/interp.png",title="Interpolator data flow"]

The Interpolator is capable of performing an Add, Right Shift, Mask, and Sign Extend all within a single CPU cycle, with feedback from previous cycles into the input. The datasheet indicates that this is useful for pixel blending and certain audio synthesis operations.

The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-interpolator.ads[RP.Interpolator] package directly exposes the registers of the Interpolator peripheral, which are declared as `RP.Device.INTERP_0` and `RP.Device.INTERP_1`. We don't have an example for this yet because we don't entirely understand it. You could write one!

=== Flash
The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp-flash.ads[RP.Flash] package erases and programs the flash chip that your program is stored in, which is useful for saving settings or data. Offsets are relative to the beginning of flash. `Erase` works on 4096 byte sectors and `Program` on 256 byte pages.

[source,ada]
----
declare
    use RP.Flash;
    Offset : constant Flash_Offset := 1024 * 1024; --  1 MB from the start of flash
    Data   : aliased HAL.UInt8_Array (1 .. Page_Size) := (others => 16#42#);
begin
    Erase (Offset, Sector_Size);
    Program (Offset, Data'Address, Data'Length);
end;
----

The flash chip can't be read while it is being erased or programmed, so code can't be executed from it either. These procedures are placed in RAM, but any interrupt handler that runs during the operation will crash if it is in flash. Interrupts that may execute from flash must be masked, and if the second core is running, it must only execute code from RAM or the boot ROM for the duration. It's up to you to pick an offset that doesn't overlap your program.

`Unique_Id` returns the 64-bit serial number of the flash chip, which can be used to tell boards apart.

The `RP.Flash.Cache` package controls the cache that sits between the CPU and flash. The `Disable` procedure can be used to temporarily turn the cache off and measure its performance impact on your program.

=== Watchdog
The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-watchdog.ads[RP.Watchdog] package resets both processors if `Reload` isn't called before a timeout expires. It is only available on the RP2040.

[source,ada]
----
RP.Watchdog.Configure (Timeout => 1_000); --  milliseconds
RP.Watchdog.Enable;

loop
    --  If this loop takes longer than a second, the chip resets
    RP.Watchdog.Reload;
end loop;
----

=== ROM functions
The RP2040's ROM contains a library of useful functions that can be accessed via a symbol lookup table. The https://github.com/JeremyGrosser/rp2040_hal/blob/3.x/src/rp2040/rp-rom.ads[RP.ROM] package provides an Ada binding to some of them, including fast memory copies, bit manipulation, and `reset_to_usb_boot`, which restarts the chip in BOOTSEL mode. It is only available on the RP2040.

The Cortex-M0+ has no hardware floating point unit, so the RP2040 runtimes use the ROM's floating point routines to implement floating point arithmetic. Use the standard `Ada.Numerics.Elementary_Functions` package for trigonometry. The RP2350's Cortex-M33 has a hardware floating point unit.

=== Multicore
Both chips have two CPU cores. The runtime starts the second core and schedules tasks on it. A task runs on the first core unless it is assigned to the second with the `CPU` aspect.

[source,ada]
----
task Blinker
    with CPU => 2;
----

Tasks communicate with each other through protected objects or `Ada.Synchronous_Task_Control`, regardless of which core they're running on. Interrupt handlers are assigned to a core by the name used in `Attach_Handler`. See the https://github.com/JeremyGrosser/pico_examples/tree/3.x/multicore/src[multicore example] for usage information.

If you don't need the second core, setting `Max_CPUs` to 1 saves some memory and frees the resources that the runtime reserves for communication between cores.

[source,toml]
----
[configuration.values]
light_tasking_rp2040.Max_CPUs = 1
----

[#custom_board_support]
=== Custom board support
The focus of this project is to support the Raspberry Pi Pico and Pico 2 development boards, but these libraries are portable to any board that uses the RP2040 or RP2350. A board differs from the Pico in three ways that matter to software: the flash chip, the crystal oscillator, and the pinout.

==== Flash and crystal oscillator
The second stage bootloader, linker script, and oscillator startup are provided by the runtime, and are selected with its `Board` configuration variable. The runtimes know about many popular boards.

[source,toml]
----
[configuration.values]
light_tasking_rp2040.Board = "adafruit_feather_rp2040"
----

If your board isn't in the list, set `Board` to `generic_board` and describe it with the `XOSC_Frequency`, `XOSC_Startup_Delay_Mult`, and `Flash_Chip` (RP2040) or `Flash_Size` (RP2350) variables. The https://github.com/damaki/community-bb-runtimes/blob/main/rp2040_src/README.md#board-configuration[RP2040] and https://github.com/damaki/community-bb-runtimes/blob/main/rp2350_src/README.md#board-configuration[RP2350] runtime documentation lists the supported boards and the meaning of each variable.

[source,toml]
----
[configuration.values]
light_tasking_rp2040.Board = "generic_board"
light_tasking_rp2040.XOSC_Frequency = 12000000
light_tasking_rp2040.Flash_Chip = "w25q32jv"
----

These variables are set in the `alire.toml` of the application, which is the crate that depends on the runtime.

==== Pin definitions
It is unlikely that your custom board has the same pinout as the Pico. We recommend creating a new `yourboardname_bsp` Alire crate that depends on rp2040_hal and contains a package that defines symbolic names for GPIO pins that match a schematic net name or silkscreen that a user of your board would recognize, along with drivers for the board's components. If the board uses an RP2350, the BSP crate can set `rp2040_hal.Device` so that applications don't have to.

The https://github.com/JeremyGrosser/pico_examples/blob/3.x/feather_rp2040_bsp/src/feather_rp2040.ads[Adafruit Feather RP2040 example] provides pin definitions for a custom board, and https://github.com/JeremyGrosser/pico_examples/tree/3.x/feather_rp2040_blink[feather_rp2040_blink] is an application that uses it.

=== Optimization

==== Binary size
The `-Wl,--gc-sections` linker switch removes code and data that your program never references, which substantially reduces the size of the binary. It is not enabled by default.

The RP2040's XIP cache is only 16 KB and reads from flash ROM are fairly slow compared to CPU cycle time and memory access. The `RP.Flash.Cache.Disable` procedure can be used to temporarily disable the cache and measure its performance impact on your program.

==== Switches
While compile-time optimizations are no substitute for efficient algorithms, GCC can usually make your code fast and small enough for all but the most demanding tasks. Flags can be passed to the compiler and linker in a gpr project file using the `Switches` option. The GNAT user guide includes a https://gcc.gnu.org/onlinedocs/gnat_ugn/Alphabetical-List-of-All-Switches.html[list of all available switches]. The example below shows the ones I use most frequently.

[source,ada]
----
   package Compiler is
       for Switches ("Ada") use (
           "-Os",           --  Optimize for size. Use -O2 or -O3 for performance optimization
           "-g",            --  Generate debug symbols
           "-gnatwa",       --  All warnings
           "-gnatwl",       --  Elaboration warnings
           "-gnatVa",       --  Validity checks. Execution faster without these, but
                            --  constraints are a good idea.
           "-gnatyg",       --  Style checks. Not required, but recommended.
           "-gnatyM120",    --  Line length. Controversial.
           "-gnatyO",       --  Overriding subprograms must be explicitly marked
           "-gnata",        --  Enable assertions. Pre and Post conditions are enforced.
           "-gnatn",        --  Enable inlining. Procedures also need to be marked "with Inline" and
                            --  compiled with -O2 to actually be inlined
           "-gnatQ",        --  Keep going after errors
           "-gnatw.X",      --  Hide No_Exception_Propagation warnings when using a
                            --  light-tasking runtime, where exceptions are always crashes.
           "-gnatwB",       --  Hide Warn_On_Bad_Fixed_Value. Values assigned to fixed types may be
                            --  truncated to the nearest 'Small
           "-fstack-usage", --  Output stack usage information.
                            --  Generates .su files that can be used for stack analysis later.
           "-ffunction-sections", --  Every function gets it's own ELF section
           "-fdata-sections"      --  Every variable gets it's own ELF section
       );
   end Compiler;

   package Linker is
      for Default_Switches ("Ada") use
          Runtime_Build.Linker_Switches & (
              "-Wl,--gc-sections",       --  Discard unused ELF sections
              "-Wl,-print-memory-usage", --  Outputs memory and flash usage after linking
              "-Wl,-Map=main.map"        --  Generate a memory map file for later analysis
          );
   end Linker;
----

[#migrating_from_2_x]
=== Migrating from 2.x
rp2040_hal 3.0 is a major release with many incompatible changes. The xref:change_log[change log] has the complete list. These are the steps most projects need to take.

. Add a dependency on a runtime crate, such as `light_tasking_rp2040`. In your project file, replace `with "pico_bsp.gpr"` or `with "rp2040_hal.gpr"` with `with "runtime_build.gpr"`, take `Target` and `Runtime` from `Runtime_Build`, and use `Runtime_Build.Linker_Switches`. See xref:create_a_new_project[Create a new project].
. Remove `rp2040_hal.Flash_Chip`, `rp2040_hal.Use_Startup`, and `rp2040_hal.Interrupts` from `alire.toml`. The board is now selected with the runtime's `Board` variable.
. Delete calls to `RP.Clock.Initialize`, `RP.Clock.Enable`, `RP.GPIO.Enable`, and `RP.Device.Timer.Enable`. The runtime configures the clocks and the drivers enable what they need.
. Replace `RP.Device.Timer.Delay_Milliseconds` and friends with `delay`, and `Delay_Until` with `delay until` and `Ada.Real_Time`.
. Rewrite interrupt handlers as protected procedures with `Attach_Handler`. `RP_Interrupts`, `RP.GPIO.Interrupts`, and `RP.GPIO.Set_Interrupt_Handler` are gone. See xref:interrupts[Interrupts].
. Refer to PIO blocks by number rather than `RP.Device.PIO_0'Access`, and call the `RP.PIO` subprograms with the block as the first argument: `Enable (P)` rather than `P.Enable`.
. In `DMA_Configuration`, replace `Increment_Read => True` with `Read_Address => Increment`, and likewise for `Increment_Write`.
. Move large local variables out of the main procedure. See xref:stack_size[Stack size].
. If you relied on the default drive strength of `RP.GPIO.Configure`, note that it changed from 4 mA to 2 mA. Pass `Drive => Drive_4mA` to keep the old behavior.
. Replace `RP.Multicore` with tasks and `RP.ROM.Floating_Point` with `Ada.Numerics`.
. Use the port objects declared in `RP.Device` rather than declaring your own. The drivers no longer use the `RP2040_SVD` register types in their specifications, so declarations like `RP.UART.UART_Port (0, RP2040_SVD.UART.UART0_Periph'Access)` no longer compile.

`RP.I2C`, the low level I2C driver with target mode support, has no replacement in 3.0.

== API reference
The package specifications are the reference for the API. https://github.com/JeremyGrosser/rp2040_hal/tree/3.x/src[Read the .ads files] in rp2040_hal: drivers shared by both chips are in `src`, and those that differ are in `src/rp2040` and `src/rp2350`.
